# 差异化说明：我们不重复官方，我们做增量

> 目的：回应"气候智慧茶园/采摘期预测"选题拥挤、且官方气象已覆盖部分能力的质疑。
> 一句话：**官方气象解决"要不要防"，TeaWindow 解决"哪块地、多大概率、今天采还是防、给谁执行"。**

## 对比表
| 维度 | 杭州市气象局现有能力 | TeaWindow（本方案） |
|---|---|---|
| 空间粒度 | 产区/区域级 | **地块级**（地形/坡向 → 霜冻易感） |
| 风险类型 | 以霜冻为主、单一 | **倒春寒 × 高温 × 干旱 × 连阴雨 复合** |
| 不确定性 | 单值/短信 | **概率校准 + 122 成员集合概率 + 置信区间** |
| 输出 | 气象要素 / 预警短信 | **可行动决策**：采摘窗口 + 养护建议 + **采摘排班** |
| 用户 | 部门/管理者 | **直接面向茶农/采茶队**，白话可执行 |
| 闭环 | 预警 → 短信 | **预警 → 行动 → 反馈 → 验证**（90 天计划） |
| 数据可信度 | —— | 台站观测交叉验证(r=0.98) + 官方开采日外部真值(MAE≈1.8天) |

## 三个"增量"的证明（均有产出）
1. **下沉到地块**：`report/terrain` + 仪表盘「地块级地形/调度」面板 → 6 地块差异与抢采优先级。
2. **复合 + 不确定性**：`models/calibration.json`（Brier↓）、`data/processed/ensemble.json`（P(霜冻)/P(高温)）。
3. **从预测到决策**：`src/scheduler.py` 在**每日产能约束**下输出**未来 7 天采摘排班**（同类作品少见）。

## 边界（主动划清，避免被误判为"大而全"）
- **不做**：产量预测、病虫害识别、气象要素预报本身。
- **做**：风险识别 → 可行动建议 → 调度 → 验证闭环。

## 为什么官方没做、我们能做
- 官方重"公共预警"，少"地块级经营决策"；
- 我们成本极低（公开数据 + 纯 numpy），可做**面向个体茶农的精细化与排班**；
- 定位是**与官方互补**，而非替代（灾害预警仍以官方为准）。

## 一句话电梯陈述
> "气象台告诉你**要不要防**；我们告诉你**哪块地最危险、明天先采哪块、要不要提前抢采**。"
